# Pitfalls Research

> **Scope note:** Scope narrowed 2026-11-21 to AC only (D-17, `.planning/phases/01-course-matcher/01-CONTEXT.md`). Multi-faculty content below is reference for a later phase.

**Domain:** AI-assisted web app for incoming Erasmus+ students at UPT Timisoara (course matcher, paperwork checklist, cross-faculty timetable builder with LLM/vision extraction and .ics export), built by an AI-agent workflow in ~2 days
**Researched:** 2026-11-20
**Confidence:** MEDIUM overall. HIGH on engineering failure modes (Unicode, iCalendar/DST, LLM grounding, demo operations), which are well established. MEDIUM on UPT-specific data shapes, because the catalogue and timetable pages were only located through search, not opened and parsed. LOW on UPT's parity-numbering convention, which must be checked against a real timetable PDF.

Known data locations found during research (verify in Phase 0):
- Course catalogue: HTML page at `international.upt.ro/en/course-catalogue/`, referenced from the 2025-26 KA131/KA171 factsheets. Older years used different URLs, so links in older material rot.
- Timetables: per-faculty PDFs with version suffixes in the filename (e.g. `TI_I_sem_I_01.10.2025_v2.pdf` on sc.upt.ro, `I_C_Sem_1_2025-2026_v_4.pdf` on mec.upt.ro). Faculties republish revised versions, so any file you cache can already be stale.
- Calendar and timetable hub: `upt.ro/en/students/calendar-timetables`.
- Mobility guides are year-specific pages (`Incoming-students-2023-2024`, etc.). The one you fetch may describe a past year.

## Critical Pitfalls

### Pitfall 1: LLM invents or "improves" admin/legal advice

**What goes wrong:**
The paperwork checklist or stretch chatbot states a visa step, deadline, fee or office hour that is not in any official UPT document, for example a wrong RON deposit amount, a wrong office number, or "Non-EU students need X" when the guide says Y. A student acts on it. The project's own constraint says wrong paperwork advice harms students.

**Why it happens:**
The model fills gaps fluently. Citizenship (EU/EEA vs Non-EU), grant (KA131 vs KA171) and mobility type (Study vs Traineeship) create a branching matrix, and the model "completes" cells the guide never covers. Free-text generation per user is the most hallucination-prone design.

**How to avoid:**
- The checklist is a hand-curated static JSON/TS data file (item, applies-to predicate over the 4 onboarding answers, deadline rule, `source_url`, `source_quote`, `verified_on`). The LLM is NOT in the generation path. Filtering by predicate is plain code. This is also faster to build and 100% deterministic on demo day.
- Every item must carry a source citation. UI renders the source link. An item with no source cannot ship.
- Add a persistent "Informational only. Confirm with incoming@upt.ro" notice, and show the `verified_on` date.
- Any item you cannot source from a UPT page: omit it or mark "Ask the International Office" rather than guess.
- Stretch RAG chatbot: retrieve-then-answer only, strict "answer only from the provided passages, otherwise say you do not know and point to incoming@upt.ro", return passage IDs, and render the quoted passage. Refuse when top retrieval score is below threshold. Ship it only if the checklist and matcher are done and green.

**Warning signs:**
Checklist items with no `source_url`. Answers containing specific numbers (RON amounts, hours, office numbers) that you cannot find via text search in the source corpus. The model answering a question about something no guide covers instead of refusing.

**Phase to address:**
Paperwork phase (data modeling and curation). Chatbot, if built, needs its own grounding test with 5 out-of-scope questions that must be refused.

### Pitfall 2: Matcher "explanation" hallucinates facts about UPT courses

**What goes wrong:**
The AI reason says "this course covers X and is taught in English" when the catalogue says neither. Or the UI shows ECTS/semester/English status that the LLM made up because the structured fields were missing and the prompt let it answer from memory. Learning Agreement is a binding academic document, so a wrong ECTS value propagates.

**Why it happens:**
Prompt receives only course titles, so the model fabricates details. Metadata is generated by the LLM instead of read from the data. "English status" is ambiguous in UPT data (fully taught in English vs English tutoring/materials), and a boolean collapses it.

**How to avoid:**
- Structured fields (ECTS, semester, year, faculty, evaluation, English status) come from the data record, never from the LLM output. The LLM returns only `{course_id, score_adjustment?, reason}` and `course_id` is validated against the catalogue. Drop any ID not in the catalogue (hard filter).
- Pass the candidate's real description/syllabus text into the prompt and instruct "only reference topics present in the candidate text; if the description is empty, say 'limited information'".
- English status is a 3-value enum: `taught_in_english | english_materials_or_tutoring | unknown`. Show `unknown` honestly instead of defaulting to a guess.
- Use structured output (JSON schema / tool use) and parse-validate. Never regex free text.
- Show "Suggestion only. Your coordinators approve the Learning Agreement" in the UI.

**Warning signs:**
Reasons mentioning topics absent from the candidate record. ECTS values that differ from the catalogue. Empty/`null` fields rendered as plausible text.

**Phase to address:**
Matcher phase (data schema first, then prompt). Verify with 5 spot checks against the live catalogue before demo.

### Pitfall 3: Embedding match quality is bad and nobody measures it

**What goes wrong:**
Top-5 results look random or are dominated by noise: courses with similar boilerplate words ("Fundamentals", "Introduction to", "Lab"), Romanian-titled courses never matching English queries, short titles ("Physics") matching everything. The headline demo (the Core Value) gets a nonsense top result.

**Why it happens:**
- Catalogue titles are short and context-free. Cosine on title-only embeddings is weak.
- Mixed-language corpus: some entries Romanian, some English. Using an English-only embedding model degrades cross-lingual recall. Some models also behave differently on diacritics.
- Home course descriptions are free text of wildly different length and quality, compared against terse catalogue entries (asymmetric length).
- Team never builds even a tiny evaluation set, so "looks fine" on 2 hand-picked queries.
- Over-engineering: setting up a vector DB for a catalogue of probably a few hundred to a couple thousand rows.

**How to avoid:**
- Catalogue is small: keep embeddings in memory or a JSON/SQLite blob, brute-force cosine. No vector DB service.
- Use a multilingual embedding model (e.g. Voyage multilingual or OpenAI text-embedding-3, or a multilingual open model) and embed `title + faculty + description + level` as one document, not title alone. Normalize diacritics before embedding (Pitfall 6).
- Two-stage pipeline: embedding retrieves top ~15-20, then Claude reranks and writes the reason in ONE call (batch candidates into a single prompt, structured output). This fixes most embedding noise cheaply and is the standard pattern.
- Pre-compute and persist catalogue embeddings at build time. Embedding at request time is a latency and cost trap.
- Build a 10-15 pair golden set (home course -> expected UPT course) in the first hour of the matcher phase, using realistic Erasmus cases (e.g. Data Structures, Linear Algebra, Thermodynamics). Print top-3 for each as a script. Run after every change.
- Strip stop-noise ("Introduction to", "Fundamentals of") only if the golden set shows it helps. Do not guess.
- If the student gives only a title with no description, ask for ECTS/description or let the LLM expand the title into a 2-sentence description before embedding (HyDE-style), flagged as expanded.

**Warning signs:**
Same 3 generic courses appear for unrelated queries. Scores bunched (all 0.78-0.82) so ranking is meaningless. Romanian-titled courses never appear for English queries.

**Phase to address:**
Matcher phase. Golden set gate before building UI polish.

### Pitfall 4: Scraping/parsing UPT sources eats the whole 2 days

**What goes wrong:**
The team spends day 1 on a generic crawler and PDF table parser, hits inconsistent layouts across 10+ faculty subdomains, and has no data when it is time to build the UI. Or live scraping at demo time fails because a UPT site is slow, down, or changed.

**Why it happens:**
Each faculty publishes timetables differently (PDF per year/series, HTML tables, Excel exported to PDF, scanned images). Filenames are versioned and republished. Catalogue is HTML that may be paginated or JS-rendered. Tendency to automate when a one-time manual/semiautomated ingest is cheaper.

**How to avoid:**
- Seed data, not live scraping (matches the stated constraint). One offline ingest script run once, output committed to the repo as JSON. Runtime never touches upt.ro.
- Fetch catalogue with `curl`/Python `requests` and check first whether the content is server-rendered. Only reach for headless browser if it is JS-rendered.
- Time-box ingestion: 90 minutes for the catalogue. If a field cannot be parsed, leave it `unknown` and move on.
- For timetables, do NOT build a general PDF-table parser. Pick 2-3 faculties the demo will use (AC, ETc/sc, MEC), take 3-5 representative PDFs, and run them through the Claude vision/PDF extraction (the project's own Module 3 feature) with a schema, then human-review the JSON. This doubles as pre-seeded demo data.
- Save the raw downloaded files in the repo (`data/raw/`) with download date, so results are reproducible and the demo does not depend on the network.
- Quick triage per PDF: is it text-based (`pdftotext -layout` returns text) or scanned (empty output)? Text PDFs: extract text with layout preserved and feed to Claude. Scanned/image PDFs: render pages to PNG (pdftoppm, 150-200 DPI) and use vision.

**Warning signs:**
More than 2 hours without a single committed `courses.json`. A "scraper" with per-faculty `if` branches. Network calls in request handlers.

**Phase to address:**
Phase 0/Data ingestion, before the matcher UI. Hard time-box.

### Pitfall 5: Vision extraction of timetable grids silently drops or misplaces cells

**What goes wrong:**
Merged cells (a lecture spanning two hours or two groups), rotated day labels, tiny font, color-coded legends, "p"/"i" parity marks, and multi-line cells produce wrong time slots, swapped rooms, a missing lab, or a course assigned to the wrong day. The extractor looks confident. The user's schedule then silently conflicts or shows a free slot that is actually busy.

**Why it happens:**
Vision models read grids positionally and are weakest at spanned cells and rotated text. Models normalize and "tidy" ambiguous cells. Low-resolution screenshots lose small characters (B410 vs B418, 8 vs 6). Long single-prompt full-page extractions truncate or skip rows.

**How to avoid:**
- Treat extraction as a draft, never as truth: always show an editable review table (day, start, end, course, type, room, parity, group) before saving. Highlight low-confidence rows. This is the single most important mitigation and is also good UX.
- Use a strict JSON schema via tool use with explicit fields: `day`, `start`, `end` (24h HH:MM), `course`, `type` (lecture/seminar/lab/project), `room`, `parity` (`every|odd|even`), `group/subgroup`, `confidence`, `raw_text`. Keeping `raw_text` lets the user and you compare.
- For text-layer PDFs, prefer `pdftotext -layout` or the PDF input (text plus page images) over screenshots. Only fall back to image-only when no text layer exists.
- Render images at adequate resolution (the model downsizes very large images, and tiny font needs about 150-200 DPI crops). Split big grids into per-day or per-half-page crops rather than one giant image. Rotate rotated pages upright before sending.
- Post-validate in code: times within 08:00-21:00, start < end, durations in {60, 90, 100, 120, 180}, room matches `^[A-Z]{1,3}\s?\d{2,4}[A-Za-z]?$` or the known pattern, no two rows with identical day/time/course. Reject and re-ask on failure (one retry).
- Row-count sanity: count non-empty cells independently (or ask the model to also return `row_count_seen`) and compare.
- Pre-extract and cache the 2-3 demo timetables ahead of time (see Pitfall 12). Live upload in the demo is a bonus, not the critical path.

**Warning signs:**
Extractor output with zero overlaps on a timetable you know is dense. Duration column all identical (model flattened merged cells). Rooms that do not exist in the room-code table.

**Phase to address:**
Schedule phase. Build review/edit UI in the same phase as extraction, not after.

### Pitfall 6: Romanian diacritics: cedilla vs comma-below breaks search, joins and dedup

**What goes wrong:**
`Timișoara` (s with comma below, U+0219) vs `Timişoara` (s with cedilla, U+015F) look identical but do not match. Same for `ț` U+021B vs `ţ` U+0163. Also `ă â î` as precomposed vs base letter plus combining mark (NFC vs NFD), and PDF extraction that drops diacritics entirely (`Automatica` vs `Automatică`). Result: course dedup fails, exact-match lookups for faculty or room names miss, keyword search returns nothing, embedding inputs differ for the same string, `<select>` filters show duplicates.

**Why it happens:**
UPT PDFs and pages were authored over many years; older Windows encodings produce cedilla variants. PDF text extraction may emit NFD or private-use glyphs. The bug is invisible to the eye.

**How to avoid:**
- One `normalize_ro()` function applied at ingest AND at query time: Unicode NFC, then map ş->ș, ţ->ț, Ş->Ș, Ţ->Ț (U+015F->U+0219, U+0163->U+021B, U+015E->U+0218, U+0162->U+021A). Keep the display value in canonical comma-below form.
- Separate `search_key()`: NFKD, strip combining marks, lowercase, collapse whitespace. Use for matching, dedup and embeddings input. Never for display.
- Add a 5-line unit test with all four code points and a Windows-1250/legacy sample. Run over the full catalogue and print any char outside Basic Latin plus the Romanian set, to catch mojibake (`Ã£`, `?`, `�`).
- Ensure files are read/written UTF-8 explicitly (Windows default code page cp1252 is a real risk on this dev machine: use `encoding="utf-8"` in Python, `-Encoding utf8` in PowerShell; `Get-Content` without it corrupts).
- .ics output: write UTF-8 and fold lines at 75 octets, not characters (diacritics are 2 bytes; folding mid-character corrupts the file).
- Fonts: confirm the chosen web font includes ș/ț (comma-below glyphs). Some fonts render fallback glyphs or cedilla shapes.

**Warning signs:**
The same faculty appears twice in a dropdown. A search for "Automatică" or "Timișoara" returns nothing despite visible matches. `?` or `Ã` in the data.

**Phase to address:**
Data ingestion phase (normalization utility is a Day-1 hour-1 task). Tested again in Schedule (.ics).

### Pitfall 7: Odd/even week parity computed wrong (and anchored to the wrong calendar)

**What goes wrong:**
Classes marked "săptămână impară" / "pară" (or `S1/S2`, `I/II`, `sapt. 1`, `1-7`) are placed on the wrong weeks, so every alternate-week lab appears one week off. Or parity is derived from ISO week number, which does not match the university's teaching-week numbering.

**Why it happens:**
Parity is relative to the university's own teaching-week count, which starts on the semester start date (and may exclude holiday or exam weeks), not the calendar year. ISO week parity flips at year boundaries (some years have 53 weeks) and has no relation to Week 1 of the semester. Each faculty may mark parity differently in its grid. Which week is "1" can also differ between faculties' conventions. I could not confirm the AC faculty's legend from search, so this is a verification item, not an assumption.

**How to avoid:**
- Parity anchor = semester Week 1 Monday, read from the official UPT structure-of-academic-year page (`upt.ro/en/students/calendar-timetables`) and stored as a config constant per semester. Compute `teaching_week = floor((date - week1_monday)/7) + 1`, `parity = odd if teaching_week % 2 == 1`.
- Record, per extracted row, a normalized `parity: every|odd|even` and keep the original token in `raw_text`. Show the legend mapping in the review UI.
- Decide explicitly (and document) whether holiday weeks consume a parity step. Check with one real timetable and the calendar: this is the single highest-value check. If unsure, state the assumption in the UI.
- Generate .ics by expanding into explicit event instances for the teaching weeks of the semester (about 14 instances), not a fragile `RRULE;INTERVAL=2` with a DTSTART in the wrong week. Explicit expansion makes holidays trivial (just skip dates) and the parity logic testable.
- Test: for a known date (e.g. a Tuesday in teaching week 3), assert the odd-week class is present and the even-week class is absent.

**Warning signs:**
An alternate-week lab shows up on the first week when the faculty says even. Conflict detector reports no conflicts for two classes that share a slot but opposite parity, or false conflicts for them (parity ignored in overlap check).

**Phase to address:**
Schedule phase (data model must include `parity` from the first commit; overlap detector must be parity-aware: two rows overlap only if times overlap AND parity sets intersect).

### Pitfall 8: Romanian academic calendar and holidays ignored

**What goes wrong:**
Exported .ics schedules classes on days with no teaching: 30 Nov (St. Andrew), 1 Dec (National Day), Christmas/New Year break, Orthodox Easter (moveable date, differs from Western Easter), 1 May, 1 June, Pentecost/Rusalii, 15 Aug, plus university-specific vacation weeks and exam sessions. Students show up to empty classrooms, or the calendar shows classes during the winter session.

**Why it happens:**
The team generates "every Tuesday for N weeks" without a calendar. Orthodox Easter is not computed. The semester structure (teaching weeks, holiday weeks, exam session, resit session) is published per year and changes.

**How to avoid:**
- A small `calendar_2026_27.json`: semester start, teaching-week count, holiday ranges, exam-session range, copied from the official UPT calendar page with the source URL. Hard-code the public holidays for the year (do not compute Orthodox Easter at runtime; look up the date).
- The .ics generator consumes this file: skip holiday dates, stop at end of teaching weeks.
- Note the demo date itself: 30 Nov and 1 Dec 2026 fall soon after the demo and are the most visible test case. A sample export that puts a class on 1 Dec is an embarrassing, easy-to-spot bug. Seed a test for it.
- Be explicit in UI about which semester/year the data covers.

**Warning signs:**
An event dated 1 Dec or 25 Dec in the exported file. No calendar file in the repo.

**Phase to address:**
Schedule phase, same time as parity (shared calendar module).

### Pitfall 9: .ics timezone, DST and format bugs

**What goes wrong:**
Events appear one hour off after the DST change, show in UTC to a student whose phone is in their home timezone, or the file is rejected by Apple/Outlook while Google accepts it. Typical sources: floating times, `Z` (UTC) times for recurring events, TZID without a VTIMEZONE block, missing UID/DTSTAMP, unfolded long lines, wrong line endings.

**Why it happens:**
Romania uses Europe/Bucharest (EET UTC+2, EEST UTC+3). DST transitions occur on the last Sunday of March (2027-03-28) and last Sunday of October (2026-10-25 is already past for semester 1, but semester 2 from February crosses the March change). Recurring or explicitly-UTC-converted events drift by an hour after the switch. iCalendar is picky about syntax and different clients are tolerant to different degrees.

**How to avoid:**
- Do not hand-write .ics. Use a library (`ics` / `ical-generator` for JS, `icalendar` for Python) and pass an IANA timezone, rather than converting to UTC yourself.
- Emit `DTSTART;TZID=Europe/Bucharest:20261123T100000` with a VTIMEZONE component for Europe/Bucharest (ical-generator and icalendar can include one via timezone helpers). Do NOT convert wall-clock class times to UTC then back.
- If expanding into explicit instances (Pitfall 7), each instance is a plain wall-clock time in the zone, so DST is a non-issue. Only the zone declaration must be correct.
- Every VEVENT needs a stable `UID` (hash of course+date+start), `DTSTAMP`, `SUMMARY`; use `\r\n` line endings; escape commas/semicolons/newlines in text; fold at 75 octets.
- Server timezone: Vercel/Node servers run UTC. Never use `new Date(y, m, d, h)` on the server for wall-clock classes. Parse times as strings or use a zone-aware library (Luxon/date-fns-tz/Temporal). Windows dev machine and UTC server giving different results is the classic "works locally" bug.
- Test: import the generated file into Google Calendar AND Apple Calendar (or an online validator such as icalendar.org/validator) and check one event before and one after 2027-03-28 shows the same wall-clock time.
- Provide a "Download .ics" button that works offline from the already-built schedule: no server round trip needed.

**Warning signs:**
Events at 08:00 showing as 07:00 or 09:00. Import produces "0 events." File lacking `BEGIN:VTIMEZONE`.

**Phase to address:**
Schedule phase (export), plus a verification step in the demo-readiness phase.

### Pitfall 10: Cross-faculty timetable data model cannot represent Erasmus reality

**What goes wrong:**
The model assumes one group/series per student. Erasmus students pick individual courses from different years and faculties, each with a different lab subgroup (e.g. 3A1 / 3A2) and parity, so "pick the timetable for group X" does not work. Conflict-free subgroup suggestion is attempted without the data model that supports it.

**Why it happens:**
Building the schedule UI from the PDF layout instead of from the entity model (Course -> Sessions -> {lecture, seminar, lab} -> Slot options).

**How to avoid:**
- Model: `Course` has many `SessionKind` (lecture/seminar/lab), each with one or more `Slot` options `{day, start, end, parity, room, group}`. The student selects one slot per required kind per course. Conflict detection runs over the selected slots only.
- Subgroup suggestion = simple backtracking/greedy over slot options (tiny search space: a few courses, a few slots each). Do not use the LLM for this; it is a 30-line deterministic function.
- Linking: Matcher course ID -> timetable course name. These come from different sources and will not match exactly. Use the same `search_key()` normalization plus a manual mapping table for the 10-15 demo courses.

**Warning signs:**
The schedule module cannot express "same course, two lab options." Conflicts computed on all slots instead of selected slots.

**Phase to address:**
Schedule phase (design the data model before any UI), with a seed timetable that includes a multi-subgroup case.

### Pitfall 11: Claude API cost, latency and rate limits hit during live demo

**What goes wrong:**
A matcher call takes 20+ seconds with a spinner, a vision extraction times out, the API returns 429/529 (overloaded) in front of the audience, or the bootcamp WiFi blocks the call. Multiple people demoing or testing simultaneously exhaust a low-tier account's rate limit. An API key ends up in client-side code or the repo.

**Why it happens:**
New or low-tier API accounts have low requests-per-minute and token limits. Vision and PDF inputs are slow and token-heavy. Sequential calls (one per candidate course) multiply latency. No streaming, so the UI looks frozen. No timeout/retry. Credits not topped up. Everybody on a bootcamp network shares one IP.

**How to avoid:**
- Check the account tier and credit balance today (Friday), not Sunday. Add credit. Know your current RPM/TPM limits from the Console and confirm the model ID you use is available to the key. Verify current model names, pricing and limits in the official docs at build time rather than trusting memory.
- Pick the fast/cheap model tier (Haiku-class) for matching rationale and reranking; reserve the larger model for vision extraction only if quality demands it. Test both on the golden set and choose on evidence.
- One batched call per query (all candidates in one prompt with structured output), not N calls. Stream the response so reasons render progressively.
- Use prompt caching for the static part (instructions, schema), set `max_tokens` tight, and set client timeout plus 1-2 retries with backoff on 429/5xx (the official SDKs retry by default; configure `maxRetries`/timeout explicitly).
- Cache by hash of (input, prompt version) in a local DB/file. Demo inputs become instant and free on repeat.
- Pre-warm: before the demo, run every demo scenario once so the cache is populated, and provide a "demo mode" fallback that serves cached/pre-computed results if the API call fails (a small `try/catch -> cached result` path).
- Key stays server-side only (env var, `.env` in `.gitignore`, never `NEXT_PUBLIC_*`/`VITE_*`). Set a monthly spend limit in the Console.
- Cap upload size and page count for the extractor (e.g. 5 pages, 5 MB) to bound cost and latency.

**Warning signs:**
Any single request over about 8s without streaming. 429s in logs during rehearsal. Spend jumping because the same input is reprocessed.

**Phase to address:**
Foundations (key handling, client wrapper with timeout/retry/cache) and Demo-readiness (pre-warm, fallback).

### Pitfall 12: Demo-day failure modes (no fallback, live dependencies, untested path)

**What goes wrong:**
Typical demo killers: network/WiFi fails; a live upload of an unseen PDF breaks; the app works only on localhost with a dev database; auth redirect URL is localhost-only after deployment; an env var is missing on the host; the first request after deploy cold-starts for 30 seconds; the browser tab holds stale state; the presenter types a home course the golden set never covered and the top match is nonsense; the presenter hits an empty state because the DB was reset.

**Why it happens:**
All effort goes into building, none into rehearsing. "It worked on my machine." Deploying for the first time at the last hour.

**How to avoid:**
- Deploy a working vertical slice on Friday night, and redeploy after every phase. First deploy happens in the first 3 hours, not the last 3.
- Freeze features Sunday morning (code freeze by roughly noon if demo is afternoon). Sunday is rehearsal, bug-fixing and the seed data, not new features.
- Write a demo script of exactly the inputs to use: 2-3 home courses known to produce great matches, one onboarding persona (e.g. Non-EU, KA171, Study), one pre-extracted timetable plus one live upload as optional bonus. Rehearse it end to end at least 3 times on the deployed URL, from a clean browser profile.
- Seeded demo account with pre-filled data so a dead API still shows a populated app. Provide a one-click "Load demo data" button.
- Record a 60-90 second screen recording of the full flow as the last-resort fallback. Keep a local build running as backup if the host fails, and have mobile hotspot ready.
- Deploy health check page: `/api/health` that reports DB reachable and API key present (without leaking it).
- Avoid dependence on live UPT sites during the demo (see Pitfall 4).

**Warning signs:**
No deployed URL by end of Friday. Last commit touching features on Sunday evening. A demo path that has never been run twice in a row.

**Phase to address:**
Every phase deploys. A dedicated final Demo-readiness phase on Sunday morning (script, seed, recording, freeze).

### Pitfall 13: Scope and schedule: three full modules in ~2 days with AI agents

**What goes wrong:**
Module 1 absorbs the whole timeline (the matcher is the most fun and the most tunable), and Modules 2 and 3 are half-built. Or all three are 70% built and none demo cleanly. The stretch chatbot starts before the core is stable. Agent-generated code accumulates unreviewed, with mismatched schemas between modules, and integration happens on Sunday.

**Why it happens:**
The requirement says "all 3 modules fully working." AI agents produce code fast but also produce plausible-looking bugs, duplicated abstractions and inconsistent types. Auth, deployment and data wrangling are invisible time sinks. Perfecting prompts is an unbounded activity.

**How to avoid:**
- Time-box per module, hard stops (suggested, 2 days is about 16-20 working hours): data and foundation 3h (including auth, deploy, normalization, seed ingest), Matcher 5-6h, Paperwork 3h (it is static data plus checkboxes, so it is the cheapest to complete), Schedule 5-6h, polish and rehearsal 3h. If a module exceeds its box, cut its scope, not the next module's.
- Define "done for demo" per module as the demo script path only. Each module ships a vertical slice first (works on seed data) and enhancements after.
- Cut list decided now, in this order: RAG chatbot first, then room-code-to-directions (use a small static lookup for the demo buildings), then live PDF upload (keep pre-extracted + paste-text path), then conflict-free subgroup suggestion (show conflicts only), last the Learning Agreement export niceties.
- Keep one shared type/schema file for Course, Slot, ChecklistItem used by all modules. Have agents extend it rather than invent local types.
- Smallest viable stack: a single full-stack framework (e.g. Next.js or similar), SQLite/Postgres via hosted provider or even file-based JSON for seed data, no microservices, no separate API server, no ORM migration ceremony beyond what is needed.
- Do not let agents refactor. Commit after each working slice so a broken Sunday change can be reverted in one command.
- Run the real app after each agent task. "Tests pass" without a clicked-through check is not enough for UI/AI flows.

**Warning signs:**
Matcher still being "tuned" at hour 12 with Module 2 untouched. More than 2 unmerged half-features. Different field names (`ects` vs `credits`) across modules.

**Phase to address:**
Roadmap structure itself: phases ordered Foundation -> Matcher -> Paperwork -> Schedule -> Demo-readiness, each ending deployed and demoable.

### Pitfall 14: Auth setup becomes a time sink

**What goes wrong:**
OAuth providers, email verification, magic-link email deliverability, redirect URI mismatches between localhost and the deployed URL, session cookie issues behind a proxy, and password reset flows consume hours. Email-based verification fails in the demo because of spam folders or SMTP limits.

**Why it happens:**
"Own accounts" sounds simple. Each provider has configuration steps outside the code. The deployed domain is not known until deploy, so callback URLs break on first deploy.

**How to avoid:**
- Use a hosted auth/DB product that gives auth for free in minutes (Supabase Auth, Clerk, or Firebase) with email+password and NO email confirmation required in the demo environment. Skip social login entirely, skip password reset, skip profile pages.
- Time-box auth to 45 minutes. If it is not working, fall back to an anonymous session (random ID in an httpOnly cookie or localStorage) that persists matches/checklist/schedule: it still satisfies "saved per user" for the demo and can be upgraded later.
- Configure the production redirect/site URL the moment the first deploy URL exists. Add the preview/prod URLs to the allow-list immediately.
- Pre-create the demo account and verify login from a fresh browser on the deployed URL.
- Do not store raw uploaded timetable files containing other people's data longer than needed (see Security).

**Warning signs:**
Login works on localhost, loops or 404s on the deployed domain. More than an hour on auth.

**Phase to address:**
Foundation phase (first 3 hours), with the anonymous-session fallback decided up front.

### Pitfall 15: Stale per-year data presented as current

**What goes wrong:**
The catalogue or guide is from 2023-24 or 2024-25 while the student arrives in 2026-27: courses discontinued, English status changed, office hours or fees changed, a different 4-question set. The app confidently shows last year's deposit amount or deadline. Search results often return older `Incoming-students-2023-2024` pages and factsheets (KA131 and KA171 factsheets are published per year).

**Why it happens:**
Search engines rank old pages. Old PDFs remain online. There is no `last_updated` captured. Year is embedded in URLs but not in the data.

**How to avoid:**
- Every dataset record and checklist item carries `source_url`, `academic_year`, `fetched_on`. Ingest script refuses sources whose URL or page header indicates a year other than the target (or flags them for human review).
- Prefer the single most recent official page (the international.upt.ro 2025-26 factsheets and current catalogue) and compare against the older ones for diffs.
- Display "Data last verified: <date>, academic year <X>" in the footer of each module.
- Ambiguity to resolve with the user now: which academic year does the demo target (the 2026-27 timetables may not be published until early October 2026 for semester 1, and semester 2 timetables appear around February). Use the most recent published timetable and label it with its year, rather than silently presenting it as the next one.
- Keep ingestion reproducible (script plus raw files) so refreshing next year is a re-run, not a rewrite.

**Warning signs:**
A year string like `2023-2024` anywhere in the checklist's source URLs. No timestamps in the data files.

**Phase to address:**
Data ingestion phase (metadata fields), Paperwork phase (source verification).

## Moderate Pitfalls

### Pitfall 16: Room-code translation (e.g. B410, Electro complex) is invented

**What goes wrong:**
The LLM or the developer guesses building/floor/wing from a room code. Wrong directions for a newly arrived student.

**Prevention:**
Use a small hand-built lookup (prefix -> building, digit rule -> floor) only for the buildings that appear in the seed timetables. Verify each against the UPT campus map. If a code is not in the table, show "location not available" plus a link to the map. Never LLM-guess. Decide the floor rule (first digit = floor) only after confirming it for at least 2 buildings. Phase: Schedule.

### Pitfall 17: Home-course input is unvalidated and prompt-injectable

**What goes wrong:**
Student-entered descriptions or uploaded PDFs contain instructions ("ignore previous instructions and ...") that alter outputs; scraped text from third-party pages does the same inside a RAG chatbot.

**Prevention:**
Put user/scraped text in clearly delimited data blocks, instruct the model to treat it as data, use structured output only, never give the model tools with side effects, and validate every ID against the catalogue. Low risk for a demo but trivial to do correctly. Phase: Matcher.

### Pitfall 18: Cost/latency of running the whole catalogue through the LLM at runtime

**What goes wrong:**
Sending the entire catalogue in the prompt on every request (or per-row calls) gives slow, expensive responses and context bloat.

**Prevention:**
Embedding or keyword prefilter to about 15-20 candidates, then one LLM call. Precompute embeddings offline. Phase: Matcher.

### Pitfall 19: PDF-to-text extraction ordering and column interleaving

**What goes wrong:**
Multi-column or table PDFs extract in reading order that interleaves cells, so "Mon 8-10 Physics Tue 10-12 Maths" columns merge. Ligatures (`fi`), hyphenation and soft hyphens corrupt Romanian words.

**Prevention:**
Use `pdftotext -layout` (poppler) or `pdfplumber` with table settings, inspect output on one real file before writing any parser; send page images to Claude when text order is unusable; strip U+00AD soft hyphens and rejoin hyphenated line breaks. Phase: Data ingestion / Schedule.

### Pitfall 20: Checklist dependencies and date logic wrong

**What goes wrong:**
Deadlines are computed relative to the arrival date with off-by-one or wrong direction ("registration within N days of arrival" vs "before arrival"); items appear in the wrong order (visa before acceptance letter). Non-EU study visa steps shown to EU students.

**Prevention:**
Model each item with `depends_on`, `deadline_rule` (`{anchor: arrival|start_of_mobility, offset_days}`) and unit-test the 4 persona combinations (2x2x2 = 8 combinations; test all). Use date-only values (no times) and a date library, avoiding timezone shifts on date-only fields (`new Date("2026-11-22")` parses as UTC and can display as the previous day in negative-offset zones). Phase: Paperwork.

### Pitfall 21: Persistence loses progress

**What goes wrong:**
Checklist ticks or the saved Learning Agreement vanish on refresh, in another browser, or after redeploy because state is in React state, localStorage on a different origin, or an ephemeral serverless filesystem (SQLite file on Vercel is wiped).

**Prevention:**
Use a hosted DB (or localStorage knowingly for anonymous mode). Never rely on a local SQLite file on serverless hosting. Test: tick, hard refresh, log in from a second browser. Phase: Foundation, verified in Paperwork.

## Minor Pitfalls

### Pitfall 22: English-first UI leaks untranslated Romanian
Source data (course titles, faculty names, room names) stays Romanian. Show original Romanian name alongside an English label (and keep the Romanian for finding signs on campus). Do not machine-translate official names on the fly; cache translations if used, and mark them as translated. Phase: Matcher/Schedule.

### Pitfall 23: ECTS and semester fields parsed as strings
"6" vs "6.0" vs "6 ECTS", semesters "1/2", "S1", "I". Normalize to integers at ingest. Sum ECTS in the Learning Agreement view (typical 30 per semester) and warn when outside range. Phase: Matcher.

### Pitfall 24: Mobile layout broken for the demo
The app is "responsive web" and a phone is a natural demo device. Timetable grids overflow on narrow screens. Use a day-list view on mobile and a grid only on wide screens. Phase: Schedule, polish.

### Pitfall 25: Uploaded personal files and PII
Uploaded timetable screenshots may contain student names, and accounts store emails. Do not log request bodies, restrict stored uploads, and avoid placing any user's data in the repo or seed. Phase: Foundation.

### Pitfall 26: Secrets or raw data committed
`.env` or API key committed; large raw PDFs bloat the repo. `.gitignore` the env file on the first commit (note `.claude/` and `.idea/` are currently untracked; ignore `.idea/` to avoid noise), commit only reasonably sized raw seed files. Phase: Foundation.

## Technical Debt Patterns

| Shortcut | Immediate Benefit | Long-term Cost | When Acceptable |
|----------|-------------------|----------------|-----------------|
| Seed JSON committed instead of live scraping | Zero runtime dependency on upt.ro, instant demo | Data goes stale each year | Always for this demo; keep ingest script re-runnable |
| In-memory brute-force cosine over precomputed embeddings | No vector DB to set up | Does not scale past ~50k rows | Yes, catalogue is small |
| Hard-coded checklist JSON with citations | Deterministic, safe, fast | Manual update each year | Yes, preferred over LLM generation |
| Anonymous session instead of full auth | Saves 1-2 hours | No cross-device login | Acceptable fallback if auth exceeds 45 min |
| Manual correction of extracted timetables | Reliable demo data | Not automatic for new faculties | Yes for seed; keep review UI for live uploads |
| Hand-built room-code lookup for 2-3 buildings | Correct directions for demo | Incomplete coverage | Yes, with "location not available" fallback |
| LLM generates structured metadata (ECTS etc.) | Skips parsing work | Hallucinated values in a legal-ish document | Never |
| Skipping tests entirely because AI wrote code | Speed | Parity/DST/diacritic bugs ship | Never for the 4 pure functions: `normalize_ro`, parity, overlap, ics generation (10-minute tests) |
| Live-only demo path, no fallback | Less work | One failure ends the demo | Never |

## Integration Gotchas

| Integration | Common Mistake | Correct Approach |
|-------------|----------------|------------------|
| Claude API | One call per candidate course; no timeout/retry; key in client bundle | One batched structured-output call; SDK timeout plus retries; key server-side only |
| Claude vision/PDF | Whole page at low resolution in one prompt; trusting output | Crop/split, adequate resolution, schema + validation, human review table |
| Claude structured output | Parsing free-text JSON with regex | Tool use / JSON schema, validate with Zod/Pydantic, one retry on failure |
| Embeddings provider | Embedding catalogue at request time; English-only model | Precompute offline; multilingual model; normalize text first |
| upt.ro / faculty sites | Scraping at runtime, trusting that URLs are stable | One-time ingest, raw files committed, record `fetched_on` and source URL |
| PDF tooling | Using naive text extraction on grids | `pdftotext -layout`/pdfplumber for text PDFs; render to image for scanned ones |
| Auth provider (Supabase/Clerk/etc.) | Localhost-only redirect URLs; mandatory email confirmation | Add prod URL on first deploy; disable email confirmation for demo; pre-create demo user |
| Hosting (serverless) | Writing to local filesystem/SQLite; UTC server vs local-time assumptions | Hosted DB; explicit `Europe/Bucharest` zone handling |
| Calendar clients | Hand-built .ics, UTC conversion, no VTIMEZONE | Library with TZID + VTIMEZONE, UID/DTSTAMP, test-import into Google and Apple |

## Performance Traps

| Trap | Symptoms | Prevention | When It Breaks |
|------|----------|------------|----------------|
| Sequential per-course LLM calls | 20-60s waits, 429s | One batched call, stream output | From 3+ home courses per query |
| Embedding catalogue at request time | Slow first byte, token spend | Precompute and load at boot | Immediately |
| Vision extraction of a full-resolution multi-page PDF | 30-90s, timeouts, high token cost | Crop pages, cap page count, run in background with progress UI, cache by file hash | Any PDF over ~3 pages |
| Cold start on serverless first hit | 10-30s first request in the demo | Ping/warm before demo; keep functions light | First request after idle |
| Several people hitting the same API key during the bootcamp demo/test window | 429/529 | Cache, backoff, demo-mode fallback, check tier | Concurrent use on a low tier (RPM-limited) |
| Large JSON catalogue shipped to the browser | Slow load on mobile | Filter server-side; send only top results | Catalogue beyond a few MB |

## Security Mistakes

| Mistake | Risk | Prevention |
|---------|------|------------|
| API key in client code or committed | Key theft, spend | Server-side only, `.gitignore`, spend limit in Console |
| Unbounded upload endpoint to Claude | Cost abuse, DoS | Auth required, size/page cap, rate limit per user |
| Prompt injection via pasted/uploaded timetable or course text | Altered output | Delimit as data, structured output, validate IDs, no side-effect tools |
| Presenting AI output as official guidance | Real harm from wrong visa/paperwork steps | Cited static checklist, disclaimers, `verified_on`, contact incoming@upt.ro |
| Logging user uploads/emails | PII leak | Do not log bodies; delete uploads after extraction |
| Missing per-user row scoping in DB | One student sees another's Learning Agreement | Row-level security / `where user_id =` on every query; test with two accounts |

## UX Pitfalls

| Pitfall | User Impact | Better Approach |
|---------|-------------|-----------------|
| Similarity score shown as a bare percent | Students over-trust 0.82 | Show High/Medium/Low plus the reason, and cite which fields matched |
| No visible ECTS/English status distinction | Student picks a course not taught in English | Distinct badges: "Taught in English" vs "English materials only" vs "Unknown" |
| Extraction result auto-saved | Wrong schedule silently persisted | Review/edit step with low-confidence highlighting before save |
| Checklist is a flat list | Student does visa steps out of order | Group by phase (pre-arrival, Week 1), show dependencies and deadlines relative to arrival date |
| Spinner with no progress on 15s AI calls | Looks broken | Stream results, show stage text ("Finding candidates... ranking...") |
| Romanian-only room/building names | Student cannot find class | Show code, building name, and floor hint; link to map |
| Empty state on first login | Demo looks lifeless | "Load sample data" and sensible defaults |

## "Looks Done But Isn't" Checklist

- [ ] **Matcher:** Often missing the ID-validation step and the golden set; verify top-3 on 10+ known pairs and that every returned course ID exists in the catalogue.
- [ ] **Matcher metadata:** Often LLM-sourced; verify ECTS/semester/English status in the UI equal the source record for 5 random courses.
- [ ] **Diacritics:** Verify searching "Timișoara", "Timişoara" (cedilla) and "Timisoara" return the same results; grep data for U+015F/U+0163.
- [ ] **Checklist:** Verify every item has a source link and test all 8 persona combinations; a Non-EU persona shows visa steps and an EU persona does not.
- [ ] **Persistence:** Tick items, hard-refresh, log in from a second browser, redeploy; state survives.
- [ ] **Parity:** Verify a known odd-week lab appears only in odd teaching weeks in the export (check week 1 and week 2 dates).
- [ ] **Overlap detection:** Verify two classes in the same slot with opposite parity are NOT flagged, and same-parity ones ARE.
- [ ] **Holidays:** Open the exported .ics and confirm no event on 2026-11-30, 2026-12-01 or 2026-12-25.
- [ ] **.ics import:** Import into Google Calendar and Apple Calendar; times correct, correct timezone, no duplicates, diacritics intact.
- [ ] **Vision extractor:** Verify against 3 real timetable PDFs that every row matches the source by eye; review UI lets a user fix a wrong cell.
- [ ] **Deploy:** App works on the deployed URL from a clean browser, with auth, with the real env vars, from a phone.
- [ ] **API failure:** Kill the network or set a bad key; app degrades to cached/demo data instead of a blank error.
- [ ] **Secrets:** `git log -p | grep -i "sk-"` finds nothing; `.env` ignored.
- [ ] **Demo script:** Run end-to-end 3 times in a row without touching the code.

## Recovery Strategies

| Pitfall | Recovery Cost | Recovery Steps |
|---------|---------------|----------------|
| Hallucinated checklist item found late | LOW | Remove or mark "ask International Office", add the source field rule |
| Embedding quality poor | MEDIUM | Add rerank stage; enrich document text with faculty/description; switch to multilingual model; re-run golden set |
| Diacritics mismatch found late | LOW | Add `normalize_ro`, re-run ingest, rebuild embeddings |
| Parity off by one week | LOW | Change the anchor constant and regenerate; if RRULE-based, switch to explicit expansion |
| .ics rejected by a client | MEDIUM | Switch to a library, add VTIMEZONE, validate with an online validator |
| Vision extraction wrong | MEDIUM | Fall back to pasted text or manual entry form; hand-correct seed JSON |
| API rate-limited at demo | LOW if prepared | Serve from cache/demo mode; switch to the screen recording |
| Auth broken on deploy | MEDIUM | Switch to anonymous session mode, pre-seeded demo user |
| One module unfinished by Saturday night | MEDIUM | Cut per the cut list; ship a static, seed-driven version of that module rather than a broken live one |
